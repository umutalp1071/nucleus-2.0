# ARCHITECTURAL REVIEW 01 — Stack Position and the Closed Loop

**Date:** 2026-07-30 · **State reviewed:** Phase 08 complete, Phase 09 not started
· **Status:** review, not plan of record. Nothing here overrides `00-ANSWER.md`
until explicitly adopted.

---

## 0. Verdict, up front

Three findings, in order of confidence.

1. **"Move down the stack" is the wrong frame.** Vertical position does not
   predict defensibility. Moving toward models/compute means competing on
   capital, which is the worst possible fight for a single operator on
   $50/month. Nucleus should not move layers.

2. **The instinct behind the question is nonetheless correct, for a different
   reason.** Nucleus today implements the *first half* of the loop you
   described and none of the second half. It produces judgment; it never
   observes outcomes and never adapts. It is an open-loop advice generator
   with unusually good cost hygiene. That, not layer position, is the real
   architectural gap.

3. **Exactly three primitives are missing, and they are cheap now and
   expensive later.** `Decision`, `Prediction`, `Observation`. Everything
   else in this document is downstream of adding those. They should go in
   *before* Phase 09, because Phase 09 as written builds a weaker version of
   `Observation` (`MetricEntry`) that would have to be ripped out.

The current architecture is, in its own terms, unusually good. The chokepoint,
the ledger-derived budget, the schema boundary, and the mock-by-default
adapters are correct decisions that most teams get wrong. Nothing below asks
you to undo any of them.

## 1. Where Nucleus actually sits — measured, not assumed

Taking the codebase as it exists (~7.7k lines, 7 AI tasks, 5 test ventures):

| Component | What it is | Layer, honestly |
|---|---|---|
| 7 task files | prompt template + Zod schema + tier | application |
| `gateway.ts` | budget preflight → cache → call → parse → repair | **orchestration + governance** |
| `budget.ts` | ledger-derived spend, pre-flight guard, tier degradation | **governance** |
| `events.ts` | append-only log of human-readable summary strings | narrative, not memory |
| `cache.ts` | `sha256(task+model+prompt)` → result, 7-day TTL | dedup, not memory |
| `store.ts` + repositories | atomic JSON, swappable backend | infrastructure |
| artifacts | stored model outputs | application |

So the answer to "is Nucleus too close to the application layer?" is: it is
*mostly* application layer, but it already contains a genuine governance
component that is better than most of what exists at that layer commercially.
That component is the asset. It is currently framed in the product as a
limitation ("$50 cap") rather than as the thing it actually is.

**The single most valuable line in the codebase is not in a task file.** It is
the invariant that `preflight` runs before `provider.complete`. Everything
else in `src/` could be regenerated by a good model in an afternoon. That
invariant is a design stance.

## 2. Why "move down the stack" is the wrong heuristic

Three arguments, strongest first.

### 2.1 Lower layers are less defensible, not more

The layer diagram implies that "fundamental" and "defensible" are the same
axis. They are not. Foundation models are the most capital-intensive,
fastest-commoditizing layer in the entire stack — price per token has fallen
roughly an order of magnitude per year, and the leading models are
substitutable behind a single OpenRouter string. Compute is a duopoly defended
by fabs and CUDA, i.e. by capital and a twenty-year software ecosystem, not by
position.

Meanwhile, Stripe sits *above* the banking rails and is close to unassailable.
Bloomberg sits above market data. Epic sits above databases. In each case the
moat is workflow lock-in, accumulated proprietary data, and trust — none of
which correlate with depth in the stack.

The correct axis is not vertical. It is: **does the system accumulate
something that a competitor holding the same model API cannot obtain?**

Against that test, Nucleus currently accumulates: nothing. Artifacts are
model outputs — reproducible by anyone with the same prompt. Events are
summary strings about the system's own actions. The cache is dedup with a
7-day TTL. Delete `.nucleus/` and you have lost a week of convenience, not an
asset.

### 2.2 The "commoditized application layer" claim is half true

Yes: wrapping a model in a chat UI is commoditized. But "application layer" is
not one thing. The crowded part is the *thin* part — a prompt, a UI, no state,
no consequences. The uncrowded part is where the application takes on
**obligations**: it must not overspend, it must be auditable, it must be right
often enough to be trusted, and it must remember.

Nucleus has already voluntarily accepted one such obligation (budget). It has
declined the other three. That is the gap, and it is available *at the
application layer* without moving anywhere.

### 2.3 Generalizing before you have a user is the failure mode you already survived

`docs/mistakes/nucleus-1.0-lessons.md` lesson #1: obsession with technical
perfection killed 1.0 by destroying momentum. Lesson #11: technically
impressive, no distribution.

"Reposition as AI governance infrastructure" is the highest-status possible
version of that same mistake. It would put a solo operator into direct
competition with LangSmith, Braintrust, Arize, W&B, and every model provider's
first-party eval product — a *more* crowded and far better capitalized fight
than "venture copilot." And infrastructure with no application on top of it is
a library nobody installs.

**Conclusion: do not change layers. Deepen the loop in place, and structure
the data so that generalizing later remains possible.**

## 3. The real diagnosis — the loop is open

Your loop:

```
Intelligence → Judgment → Execution → Measurement → Adaptation → better decisions
```

What Nucleus implements:

```
Intelligence → Judgment → [handed to a human/other tool] → ✗ → ✗ → ✗
                              (build stage is a checkbox list)
```

Three of six stages are absent. And the absence is not an oversight of
features — it is an absence of *types*. There is no shape in `domain.ts` that
can represent "here is what actually happened in the world." `Artifact` holds
claims. `NucleusEvent` holds system actions. Neither holds evidence.

This has a sharp consequence: **no amount of feature work on Phases 09–12
produces learning, because there is nowhere to put the observation.**

### 3.1 The system already generates falsifiable predictions and throws them away

This is the finding that should be most annoying. Look at what the existing
schemas already extract from the model:

| Schema field | What it actually is |
|---|---|
| `Verdict.cheapestTest` | a proposed experiment |
| `Verdict.whyNot` | a stated risk hypothesis |
| `Plan.successMetric.{metric, target, by}` | **a quantified prediction with a deadline** |
| `Plan.killCriteria` | **a pre-committed decision rule** |
| `MvpScope.riskiestAssumption` | the hypothesis most worth testing |

`Plan.successMetric.by` is a date. Nothing in the system ever reads it. The
schema design was already correct — the model is being asked exactly the right
questions — and then the answers are rendered to a card and abandoned.

Wiring these five fields into a resolution loop is not a new product
direction. It is finishing the one that is already half-built in the prompts.

### 3.2 Attribution, not measurement, is the hard part

A refinement to your framing: measurement alone does not produce adaptation.
It produces noise. Adaptation requires knowing *which decision* caused *which
outcome*, which requires lineage. Phase 09's planned `MetricEntry` (venture,
date, visitors, signups, revenue, note) is measurement without attribution —
a vanity dashboard. It cannot answer "was the ICP call right?" because nothing
links the number to the claim it tests.

Attribution is a data-model problem, not an AI problem. Which is precisely why
it is available to you now, at $0 of model spend.

## 4. The AGI test, applied component by component

Assume a model that is free, instant, and better than any human at every task
in `src/server/ai/tasks/`. What in this repository still has value?

| Component | Survives? | Why |
|---|---|---|
| `validate-idea`, `plan-venture`, `scope-mvp`, `write-landing-page`, `generate-build-spec`, `analyze-competitors`, `write-content` | **No** | All seven collapse into one prompt |
| The React UI | No | Generated on demand |
| Stage machine / `stages.ts` | Marginal | Convention, easily reproduced |
| `NucleusEvent` log | **Only if it contains outcomes** | Summary strings are worthless; resolved predictions are not |
| Artifact store | **Only as provenance** | Content is reproducible; *the record of what was decided when, on what basis* is not |
| Budget guard + chokepoint | **Yes — value increases** | More capable agents spend more. Something must bound them, and prove it did |
| Local-first data ownership | **Yes — value increases** | Trust is the scarce good when capability is abundant |
| The willingness to output `kill` | **Yes** | A general assistant optimizes for helpfulness and will not volunteer "stop." This is a *policy stance*, not a capability |
| The user's accumulated outcome history | **Yes — the only truly non-replicable asset** | Cannot be copied, cannot be prompted into existence, compounds |

The pattern is unambiguous:

> **Everything Nucleus *generates* is replaceable. Everything Nucleus
> *remembers* and *enforces* is not.**

That sentence should be the design north star. Its operational form: **generate
less, remember more, enforce harder.**

Note the second-order implication. Under abundant intelligence, the bottleneck
moves from "can we produce good judgment" to "can we trust the judgment we
were given, and can we prove what it cost and what it produced." That is a
governance and provenance problem — which Nucleus is one-third of the way into
solving already, purely by accident of the budget constraint.

## 5. Missing primitives

Ranked by (value × difficulty-to-retrofit). The first three are the ones that
matter; they are ~200 lines of Zod and repositories.

### 5.1 `Decision` — provenance for every AI-produced judgment

**Current defect, concretely.** In `validateAndAdvance.ts`:

```ts
await artifacts.create({ ..., model: "validate-idea", ... })
```

The `model` field is being populated with the *task name*. The actual model id
is never persisted anywhere except the `aiCalls` ledger, which is not linked to
the artifact. Additionally, the gateway computes `downgraded` — a signal that
this verdict came from a *deliberately cheaper model* — returns it, and the
artifact layer drops it. Only `demo` is stored.

So today the system cannot answer: which model produced this verdict? Was it
downgraded? What prompt version? What inputs fed it? Did the user accept it?
That is not a logging gap; it makes outcome attribution impossible in
principle.

```ts
export const DecisionSchema = z.object({
  id: z.string(),
  ventureId: z.string(),
  task: z.string(),
  artifactId: z.string(),
  promptVersion: z.string(),        // hash of the rendered template
  inputRefs: z.array(z.string()),   // upstream artifact ids — the lineage edge
  modelId: z.string(),              // the real one
  tierRequested: z.string(),
  tierUsed: z.string(),
  downgraded: z.boolean(),
  cached: z.boolean(),
  demo: z.boolean(),
  costUsd: z.number(),
  humanVerdict: z.enum(["pending","accepted","edited","rejected","regenerated"]).default("pending"),
  humanReason: z.string().nullable().default(null),
  createdAt: z.string(),
});
```

`inputRefs` is the important field. It turns a flat artifact list into a
**decision graph**, which is what makes "the verdict was wrong — what upstream
reasoning caused it?" answerable.

### 5.2 `Prediction` — the falsifiable claim, extracted from what the model already emits

```ts
export const PredictionSchema = z.object({
  id: z.string(),
  ventureId: z.string(),
  decisionId: z.string(),
  claim: z.string(),                   // "50 signups from r/languagelearning"
  metric: z.string(),
  target: z.number().nullable(),       // null = qualitative, resolved by judgment
  resolveBy: z.string(),               // ISO date. The entire point of the type.
  source: z.enum([
    "verdict.killCriteria",
    "plan.successMetric",
    "mvp.riskiestAssumption",
    "user",
  ]),
  status: z.enum(["open","hit","missed","void"]).default("open"),
  resolvedAt: z.string().nullable().default(null),
  resolvedBy: z.string().nullable().default(null),   // observationId
});
```

Extraction is a **pure function, no AI call** — `Plan.successMetric` already
has `{metric, target, by}`. Paying a model to reformat your own structured data
is exactly the waste `BACKLOG.md` already rejects for milestone expansion. Same
reasoning applies here.

An overdue open prediction is the single best thing a dashboard can show. It is
the only widget in the product that creates obligation rather than
entertainment.

### 5.3 `Observation` — evidence

```ts
export const ObservationSchema = z.object({
  id: z.string(),
  ventureId: z.string(),
  observedAt: z.string(),
  metric: z.string(),
  value: z.number().nullable(),
  note: z.string().nullable(),
  source: z.enum(["manual","deploy","import"]).default("manual"),
});
```

This replaces Phase 09's `MetricEntry`. The difference is not cosmetic: an
observation carries a `metric` name that *matches a prediction's metric*, so
resolution is a join rather than a human squinting at a chart.

**This is why the primitives must land before Phase 09, not after.** Phase 09
as written would ship `MetricEntry`, users would enter data against it, and
migrating it later means a data migration on user-owned files — the one
migration class you cannot do quietly.

### 5.4 Human judgment capture — the cheapest high-value change in this document

`RegenerateControl.tsx` exists. Every regenerate is a user saying "this output
was not good enough" — and the system discards both the fact and the reason.
Every rejected artifact is an unlabeled negative example going in the bin.

Adding a one-line optional "why?" to regenerate, stored on
`Decision.humanReason`, converts existing UI friction into an evaluation
corpus for free. After fifty ventures this is the most valuable file in
`.nucleus/`, and it cannot be reconstructed retroactively.

### 5.5 Evaluation harness — the thing that makes prompt edits non-vibes

There is currently no way to answer "did that prompt change make validation
better or worse." Every edit to `validate-idea.ts` is unverifiable. Given that
the product's central claim is *the willingness and ability to say kill*, this
is the most load-bearing unmeasured thing in the system.

The seed already exists: `src/server/ai/fixtures/` is deterministic. Extend it
into `tests/eval/` with ~20–30 historical ideas whose outcomes are known —
deliberately including famous false negatives (Airbnb, Dropbox) and obvious
duds. Score:

- **calibration** — of ideas scored 70+, what fraction actually succeeded?
- **kill precision** — of ideas scored `kill`, what fraction actually failed?
- **stability** — same idea, three runs, score variance. A verdict that swings
  ±25 points is a random number generator with good prose.

Run it manually before merging a prompt change; it does not need CI, and at
mid tier × 25 ideas it costs roughly a dollar.

This is also, not incidentally, the strongest marketing asset the project
could produce. "Our kill verdict has X% precision against 30 historical
ventures, here is the harness" is a category-defining claim that no competitor
in this space makes, and it is the most Peerlist-shaped artifact imaginable.

### 5.6 Policy as data (lower priority)

Tier assignments, `minTier`, retry count, `COMPETITOR_ANALYSIS_MIN_SCORE = 40`,
cap defaults — all hardcoded in TypeScript. Moving them into a versioned policy
record is what allows adaptation without a deploy, and it is the structural
difference between "an app" and "a governed runtime." Not urgent. Worth knowing
it is the natural fourth step.

## 6. Concrete defects found while reading

Independent of any strategic conclusion, these are real and worth fixing.

### 6.1 The repair retry bypasses the budget preflight

`00-ANSWER.md` §5 claims: *"Runaway cost from retries → Retries counted against
the same budget check."* The code does not do this. In `gateway.ts`, on schema
failure, the repair path calls `activeProvider.complete(repairPrompt, ...)`
directly with **no second `preflight`**. It records the cost afterward, but
recording is not guarding.

Consequence: a task that fits with $0.02 of headroom can spend roughly double
that, and the repair prompt is *longer* than the original (it appends the
original prompt plus the validation error), so the overspend is more than 2×.
The cap is soft in exactly the scenario the design says it is hard.

The document's claim is also achievable as written — either preflight the
repair, or reserve `2 × estimated` on the initial preflight. The second option
is simpler and keeps the guarantee stated in the invariant.

### 6.2 Spend is recorded after the call completes

`budget.record` runs after `provider.complete` returns. A crash between them
loses the ledger row permanently, and spend is *derived by summing the ledger*
— so the loss silently raises the effective cap. For a single-operator local
app this is low-severity, but "the system structurally cannot exceed $50" is
stated as an invariant, and this is the hole in it. A pre-write reservation row
reconciled after the response closes it.

### 6.3 `Artifact.model` stores the task name

See §5.1. Either fix the field or delete it — a provenance field that lies is
worse than no field.

### 6.4 `downgraded` is computed and discarded

The gateway knows a verdict came from a cheaper model. `validateAndAdvance`
returns it. The artifact does not store it. A user reviewing a six-week-old
verdict cannot tell it was produced under budget pressure. Given that the
product's honesty about demo mode is already carefully handled (`Artifact.demo`
with a UI marker), this is an inconsistency, not a design choice.

### 6.5 Cache TTL vs. the resolved-tier key

The cache key correctly includes the resolved model — good, and the comment
explaining why is right. But a 7-day TTL on a `validate-idea` result means the
same idea re-validated on day 8 costs money and may return a different verdict
with no record that it changed. Once `Decision` exists, verdict *drift* between
runs becomes observable and is genuinely interesting data.

## 7. Positioning

### 7.1 What is actually accumulating

Once §5.1–5.3 exist, the artifact that Nucleus uniquely produces is not advice.
It is:

> a complete, auditable, budget-bounded record of how a venture was reasoned
> about — including what was predicted, what actually happened, and whether the
> reasoning was right.

That is a **track record**. Track records compound, cannot be copied by someone
holding a better model, and get *more* valuable as intelligence gets cheaper,
because the scarce good shifts from "produce judgment" to "know whose judgment
to trust."

### 7.2 The durable framing

Current: *"AI venture copilot."*

More durable: *"a governed decision loop — it decides, it commits to a
prediction, it checks, and it keeps the receipts. Venture-building is the
first loop it runs."*

Two observations about this. First, it is a *reframing of what already exists*
plus three types, not a pivot. Second — and this is the part to hold onto —
the second sentence is load-bearing. The moment it becomes "a governed decision
loop" *without* "venture-building is the first loop," it is infrastructure with
no application, which is lesson #1 in a nicer suit.

### 7.3 The budget constraint is mis-marketed

$50/month is currently framed as a limitation the system respects. Under an
outcomes lens it is the opposite: it is the only product in this category that
can tell you **what a decision cost**. The ledger already has per-call cost and
`ventureId`. Cost-per-stage and cost-per-venture are a `GROUP BY` away.

"This kill verdict cost $0.11 and saved you three months" is the outcome
framing, it is true, it is computable from data you already store, and no
competitor can say it because none of them meter at the decision level. This is
a small change with a disproportionate positioning consequence, and it is the
natural bridge between the existing architecture and the thesis in your
question.

## 8. Migration strategy

Designed to preserve the existing plan. Phases 09–12 are good and nearly done;
this inserts one phase and re-shapes one.

### Phase 08.5 — Primitives (new, ~1 phase, no new AI tasks, ~$0 model spend)

Must land **before** Phase 09.

1. Add `Decision`, `Prediction`, `Observation` to `domain.ts` with `.default()`
   on all new fields so existing `.nucleus/` files still parse — the pattern
   already used for `buildUrl` / `emailCaptureUrl`.
2. Repositories for each; no new storage machinery.
3. `gateway.ts` returns full provenance (`modelId`, `tierUsed`, `promptVersion`);
   the venture services persist a `Decision` alongside every `artifacts.create`.
4. Pure function `extractPredictions(artifact)` — no AI call. Wired to
   `Plan.successMetric`, `Plan.killCriteria`, `MvpScope.riskiestAssumption`.
5. Fix §6.1 and §6.4 while in the file.
6. Backfill `Decision` rows for the 18 existing artifacts on first read, with
   `modelId: "unknown"`. Honest, and keeps the graph complete.

Definition of done: the workspace can render "this verdict came from
`claude-haiku-4.5`, downgraded from frontier, cost $0.03, fed by artifacts
`a1, a2`, and you accepted it."

### Phase 09 — Growth Stage (re-shaped, not rewritten)

Keep `write-content-calendar`, `write-post`, and the growth view exactly as
specced. One substitution: **`MetricEntry` becomes `Observation`**, and the
growth view's primary widget is not a chart but an **open-predictions list with
due dates**. Resolving a prediction is one click, and it writes back to
`Prediction.status`.

Net change to the phase: roughly one day, and it converts the weakest part of
the phase (manual vanity metrics) into the strongest.

### Phase 10 — Build-in-Public Engine (unchanged spec, much better input)

`selectStory.ts` gains one signal, weighted **highest**: *a prediction
resolved `missed`*. "We predicted 50 signups, we got 6, here is what we got
wrong" is the most shareable content type that exists, and it is the same
insight that already made `killed` a first-class stage. The phase's scoring
table was designed for this; it just had no data to score.

### Phase 11 — Immune System (scope extension)

Already covers incidents and repeat detection. Extend "the system notices its
own failures" from *crashes* to *bad judgment*: calibration drift, verdict
instability across reruns, predictions systematically overshooting. Same
machinery, applied to the model's output rather than the runtime's.

### Phase 13 — Calibration (new, after ship)

The eval harness of §5.5, plus a public calibration report. Deliberately after
Phase 12 — it is a credibility asset, and credibility assets are worthless
before anyone is looking.

### Not now, with triggers (add to `BACKLOG.md`)

| Item | Build it when |
|---|---|
| Policy-as-data | A policy value needs changing without a deploy |
| Decision graph as a queryable API | A second consumer of lineage exists |
| Extracting the governance kernel as a library | 10+ users, and one of them asks to run their own loop through it |
| Multi-loop / non-venture domains | The venture loop has resolved 50+ predictions |

## 9. What not to do

Recorded so it does not get re-proposed after a good night's sleep.

| Tempting move | Why not |
|---|---|
| Reposition as "AI governance infrastructure" now | Infrastructure with no application on it. Competes with well-funded incumbents. Lesson #1 in a better suit |
| Build an agent framework / orchestration layer | The gateway *is* the orchestration layer, and it is the right size. A framework is a library with no users |
| Add memory/RAG as a feature | Retrieval over your own 18 artifacts solves nothing. The missing thing is *outcome* data, not *retrieval* of existing data |
| Fine-tune on collected decisions | Needs volume you will not have for years. The eval harness captures 90% of the value at 1% of the cost |
| Chase codegen because the application layer feels crowded | Already correctly rejected in `00-ANSWER.md` §2. Nothing in this review changes that |
| Delay shipping to build the "right" architecture | The primitives are one phase. Everything else waits for users. See §10 |

## 10. The counter-argument, stated fairly

The strongest case against acting on any of this:

Nucleus has 5 test ventures and zero users. Every question in this document is
downstream of "does anyone want this at all." The empirically correct move is
to finish Phases 09–12, ship, get ten users, and let their behavior answer the
positioning question — because users will answer it better than reasoning will,
and reasoning about it now costs the one resource that killed 1.0, which was
momentum.

That argument is largely right, and it should govern §5.5, §5.6, §7 and Phase
13. It does not govern §5.1–5.3, for one reason: **those three types are cheap
to add today and cannot be backfilled.** You cannot retroactively learn which
model produced a verdict, whether the user accepted it, or what was predicted
in March. Provenance is the one category of engineering where the deadline
already passed for every artifact you did not instrument.

So the synthesis is narrow and should be executed narrowly:

> Add the three primitives. Fix the two budget defects. Re-shape Phase 09's
> metric type. Then carry on with the existing plan, unchanged, and ship.

Total cost: roughly one phase. Everything else in this document is a trigger in
`BACKLOG.md`, waiting for a user to justify it.

## 11. One-paragraph answer

Nucleus is not at the wrong layer, and moving down the stack would trade a
defensible position for a capital-intensive one. But the underlying instinct is
right: the system currently produces judgment and never learns whether the
judgment was any good, because there is no type in the domain that can hold an
outcome. Add `Decision`, `Prediction`, and `Observation`; wire them to the
falsifiable claims the prompts already extract and then discard; fix the retry
path that quietly makes the budget cap soft. Do that in one phase, before Phase
09 hardens the wrong metric shape, and then ship the existing plan without
further deviation. What makes Nucleus durable under any frontier model is not
what it generates — every task file is AGI-fodder — but what it remembers and
what it refuses to let happen: a bounded spend, an auditable decision graph,
and a track record of predictions that were checked.
