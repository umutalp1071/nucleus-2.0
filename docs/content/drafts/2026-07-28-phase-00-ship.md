# I wrote 1,318 lines before I wrote a single test

Nucleus 2.0 had a dashboard, a mock idea-analysis flow, and a localStorage
store — zero tests, zero CI. That's fine for three days of UI work. It stops
being fine the moment real AI calls with a real budget enter the picture,
which is next.

**Where it stands:** the app itself hasn't changed — same dashboard, same
flow. What's new is the harness underneath it: Vitest, a validated config
module, GitHub Actions on every push, and one `npm run verify` that gates
everything before a commit.

**The problem:** the next phase adds an AI gateway with budget math and schema
validation — exactly the kind of logic that fails silently. Nothing in the
repo would have caught a broken budget check except a human staring at a
number.

**How it works now:** one test file walks `src/` and asserts the architecture
rules directly — not linter config, just a regex over file contents.

```ts
it("only src/server/db/store.ts imports node:fs", () => {
  const violations = files
    .filter((f) => relative(f) !== "server/db/store.ts")
    .filter((f) => /from\s+["']node:fs/.test(contents.get(f)!));
  expect(violations).toEqual([]);
});
```

Three more rules like it: no client component imports server code, only one
file may ever mention the OpenRouter host, `src/lib/` stays free of Node
builtins.

**The call I made:** an ESLint `no-restricted-imports` rule instead — more
config, worse error messages, and it can't express "only *this one* file gets
an exception." A 70-line test file said exactly what I meant.

**Next:** the AI gateway itself — the one function every model call in this
app will ever go through.

Where do you draw the line between "test the logic" and "test the shape of
the codebase"?
