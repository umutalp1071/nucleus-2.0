# This post was written by the product it's about

Every build-in-public tool I've seen generates content *about* a project. None of them generate content about *themselves*, using their own commit history as the source material. Nucleus now does the second thing.

**Where it stands:** a `/content` drafts inbox has two generate paths. "Generate for this venture" scores that venture's own event log for narrative value and drafts a post about it. "Generate about Nucleus itself" reads this repo's own `git log`, the phase-completion rows in `PROGRESS.md`, and the latest entry in `learning.md`, and drafts a post about Nucleus's own development -- the exact post you're reading a version of right now. Every draft gets edited in place, approved into `docs/content/published/`, or rejected with a one-line reason that feeds the next generation as a negative example.

**The problem:** the event log has existed since Phase 01, used only to render an activity feed nobody read as marketing material. Every phase this project ships was a story someone had to write by hand, which meant the writing lagged the building -- exactly the failure mode that killed Nucleus 1.0.

**How it works now:**

```ts
export type Subject = { mode: "venture"; ventureId: string } | { mode: "self" };

// self mode: no venture, no Artifact, no Decision --
// the narrative comes from git log + PROGRESS.md + learning.md instead.
```

**The call I made:** self-documentation posts create no `Artifact` and no `Decision` row -- I rejected forcing every generated draft through the venture-artifact pipeline just for consistency. There's no venture to attach a "Nucleus wrote about itself" post to, and inventing one would be exactly the kind of fabricated provenance this project's own primitives exist to prevent.
